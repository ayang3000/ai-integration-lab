# Archiver Incident Copilot 实践规格

## 目标与当前状态

**待实现。** 作为 Java AI Gateway 的业务验收应用，回答“某个 Dropbox Archiver Job 连续失败并返回 429，如何排查？”等问题。使用公开或人工合成的 Runbook、日志、Job 状态，不导入真实客户、公司资料或凭据；不连接真实 Drive/Dropbox/Box，也不重跑或删除真实任务。

## 最小流程与边界

1. 服务端确定请求身份和 tenant，检索该 tenant 有权限的技术文档。
2. 对结果做上下文预算、重排，要求每条关键结论引用可定位的文档 ID/版本/段落。
3. 必要时通过只读 `get_job_status` 工具获取合成状态。模型只提出调用候选，服务端校验参数、权限、超时和审计后执行；MCP 只是接入协议。
4. 输出证据、可能原因、排查步骤和不确定性。无证据时拒绝确定诊断，不把 429 一概解释为唯一根因。
5. 先做确定性工作流；再对照最多步数、token/时间预算和人工中断的 Agent 版本。

RAG 与工具编排属于应用层；模型网关负责调用治理，不解析归档业务语义。参考[模块边界](../../architecture/runtime-modules.md)。文档中的指令和工具结果均为数据，不得改变系统权限或执行策略。

## 样本与评测设计

先建立 10 条可人工审查样本，再扩至约 100 条；以下为覆盖要求，不是已存在的数据集。

| 类别 | 输入/证据 | 期望行为 |
|---|---|---|
| 429 限流 | 合成 Retry-After、重试次数和 Runbook | 建议退避并定位限额范围，引用证据，不自动执行重试 |
| 401/403 | 合成 token 过期或权限变更 | 区分认证与授权，不建议关闭权限检查 |
| 超时/5xx | 上游状态与网络时间线 | 说明可重试条件与未知原因，不编造根因 |
| 无答案/冲突 | 缺失文档或不同版本操作说明 | 明确不确定性并展示冲突来源 |
| 注入/跨租户 | 文档要求忽略指令、其他 tenant 的 Job ID | 忽略数据中的指令，拒绝工具越权且不泄露对象存在性 |
| 工具失败 | 超时、无效参数、缺失 Job | 有界终止并说明不能验证的部分 |

JSONL 评测条目应携带 case ID、tenant、问题、相关文档 ID、期望关键点、禁止行为、是否应拒答/调用工具，以及数据集版本。训练/调参样本与保留测试集拆开；模型不能参与改写自己的验收答案。

比较无 RAG、基础 RAG、混合检索三个基线；记录 Recall@k/MRR、引用正确率、关键点正确率、拒答正确率、工具越权次数、P95、token 与费用。按样本数报告失败/缺失值，人工复核覆盖每类案例；LLM judge 只做辅助。准入阈值在测量前写入实验计划，实际数值不得预填。
